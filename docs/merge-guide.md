## 3. ฐานข้อมูล: สิ่งที่ต้องทำกับ DB จริง

### 3.1 ต่างจากของจริงตรงไหน (ตรวจด้วยการ diff โครงสร้าง)

| ประเภท | รายการ | ต้องทำ |
|---|---|---|
| **ตารางที่ของจริงไม่มี** | `tbl_attribute` (หัวข้อสเปค), `tbl_attribute_value` (ค่าสเปคต่อสินค้า) | **จำเป็น** — ระบบค้นหาจากสเปคและตารางเปรียบเทียบใช้สองตารางนี้ → รัน `database/merge/001_compare_tables.sql` |
| **คอลัมน์ที่เราเพิ่ม** | `tbl_attribute_value.model_code` (สเปคเฉพาะโมเดล) | รวมอยู่ใน 001 แล้ว |
| index ที่เราเพิ่ม | 6 ตัวบน `tbl_item` / `tbl_logs` | แนะนำ → `database/merge/002_indexes.sql` |
| ตารางที่ของจริงมีแต่เราลบทิ้งในสำเนา | `tbl_item_feature`, `tbl_item_type_feature`, `tbl_item_model_products` | **ห้ามลบบน DB จริง** — ในสำเนาเป็นตารางว่างเลยลบไป แต่เว็บจริงอาจใช้อยู่ |
| ตารางที่มีเฉพาะสำเนา | `tbl_item_tags_backup` | ไม่ต้องสร้าง (เป็นสำรองชั่วคราวตอนจัดแท็ก ไม่มีโค้ดใช้) |
| ต่างเล็กน้อย | ค่า default / NOT NULL บางคอลัมน์ (`tbl_item.view`, `tbl_item_model.qty`, `tbl_logs.created_at` ฯลฯ), PK ของ `tbl_item_option` (ของจริงคือ `id` ของเราคือ `itm_option_code`) | ไม่ต้องทำ — ทดสอบแล้วโค้ดทำงานได้กับโครงสร้างของจริง |

> ✅ **ยืนยันแล้ว 29 ก.ย. 2026: เว็บจริงเก็บสเปคใน `tbl_item_feature`** (`itm_code`, `title`, `desc` — 1 แถว = หัวข้อ 1 ข้อของสินค้า 1 ตัว)
> ระบบของเราไม่อ่านตารางนี้ → ต่อ DB จริงแล้วตารางเปรียบเทียบและการค้นหาจากสเปคจะว่าง จนกว่าจะจัดการตามหัวข้อ 3.4

### 3.2 วิธีรัน

```bash
# สำรองก่อนเสมอ
pg_dump -Fc -d <db จริง> -f before-compare-merge.dump

psql -v ON_ERROR_STOP=1 -d <db จริง> -f database/merge/001_compare_tables.sql
psql -v ON_ERROR_STOP=1 -d <db จริง> -f database/merge/002_indexes.sql
```

- ทั้งสองไฟล์ **รันซ้ำได้** และไม่ลบ/แก้ข้อมูลเดิม — ถ้าตารางมีอยู่แล้วจะเพิ่มเฉพาะส่วนที่ขาด
- 001 อยู่ใน transaction เดียว พังกลางทางแล้วไม่ค้างครึ่งๆ
- `002` บน production ที่ตารางใหญ่ ให้เปลี่ยนเป็น `CREATE INDEX CONCURRENTLY` (รันนอก transaction)

### 3.3 ย้ายข้อมูลสเปคจากสำเนานี้ไปของจริง (ถ้าต้องการ)

> ⚠️ **ตรวจ dump 1 ต.ค. 2026: `itm_code` ไม่ได้ตรงกับของจริงทั้งหมด** — dump (ถ่ายราว 3 ส.ค. 2026) มีสินค้า 20 ตัว (`itm-0000001`–`itm-0000020`) ส่วนสำเนานี้มีสินค้าที่ใช้งานอยู่ 38 ตัว:
> - **11 ตัว** มีอยู่ใน DB จริง — ค่าสเปค 106 ค่า ย้ายตรงได้
> - **27 ตัว** (`itm-0000021`–`itm-0000084`, สร้างในสำเนา 1–25 ก.ย. 2026) **ไม่มีใน DB จริง** — ค่าสเปค 455 ค่า · ถ้าเว็บจริงเพิ่มสินค้าหลัง 3 ส.ค. รหัสเหล่านี้อาจ**ชนกับสินค้าคนละตัว** ห้ามย้ายด้วยรหัสตรงๆ
>
> ก่อนย้ายต้องให้ทีมส่งรายการ `itm_code` + ชื่อสินค้าปัจจุบันมาเทียบ แล้วตกลงว่า 27 ตัวนี้จะสร้างใหม่บนเว็บจริง (ได้รหัสใหม่) หรือจับคู่กับสินค้าที่เขามีอยู่แล้ว

ข้อมูลสเปคที่กรอกไว้ในสำเนานี้ (38 สินค้า / 104 หัวข้อ)
ง่ายสุดคือ **ใช้หน้า "นำเข้าจาก Excel"** ของระบบนี้: ดาวน์โหลดเทมเพลตจากสำเนา → อัปโหลดเข้าระบบที่ต่อ DB จริง (สินค้าที่ไม่มีบน DB จริง ให้**ล้างช่อง `product_id`** ก่อนอัปโหลด ระบบจะสร้างเป็นสินค้าใหม่พร้อมรหัสใหม่ — ถ้าคงรหัสไว้ พรีวิวจะขึ้น error เพราะหาสินค้าไม่เจอ หรือแย่กว่านั้นคือไปแก้สินค้าคนละตัวที่รหัสชน)
(พรีวิวจะบอกทุกแถวก่อนบันทึก และหัวข้อที่ไม่มีจะถามว่าหมายถึงหัวข้อไหน) — ไม่ต้องเขียน SQL เอง
ข้อจำกัด: เทมเพลตพาเฉพาะค่าสเปคร่วม (`model_code` ว่าง) ค่าเฉพาะโมเดลต้องกรอกในหน้าโมเดลเอง

### 3.4 สเปคเดิมของเว็บจริงใน `tbl_item_feature` (✅ เลือกวิธีที่ 1 — 30 ก.ย. 2026)

> **ตัดสินใจแล้ว:** ย้ายสเปคเดิมเข้า `tbl_attribute` / `tbl_attribute_value` ครั้งเดียว แล้วแก้เว็บจริงให้อ่าน-เขียนตารางของเรา · `tbl_item_feature` เลิกใช้แต่ไม่ลบ (เก็บเป็นสำรอง) · ✅ **ยืนยันจาก dump แล้ว (1 ต.ค. 2026): ตารางว่าง → ไม่ต้องเขียนสคริปต์ 003** — dump มีข้อมูลจริงเป็นคำสั่ง `INSERT` (เช่น `tbl_logs` 39,395 / `tbl_item` 20 / `tbl_item_model` 23 แถว) แต่ `tbl_item_feature` และ `tbl_item_type_feature` ไม่มีสัก `INSERT` และ `tbl_item_feature_id_seq` = `1, false` · ข้อจำกัด: dump ถ่ายราว 3 ส.ค. 2026 ถ้าทีมเริ่มใช้ตารางนี้หลังจากนั้นจะไม่เห็น — ตอนรันบน staging ให้เช็ก `SELECT count(*) FROM tbl_item_feature;` อีกครั้ง (คำสั่งเดียว ไม่ต้องถามล่วงหน้า) · รายการด้านล่างใช้เฉพาะกรณีที่พบว่ามีข้อมูล · ยังต้องตกลงกับทีมว่าสเปคที่กรอกไว้ในสำเนา (628 ค่า) จะย้ายขึ้นไปด้วยหรือไม่ — สคริปต์ 003 ไม่รวมส่วนนี้

ของเขาเก็บหัวข้อเป็น**ข้อความอิสระต่อสินค้า** (`title`) ส่วนของเราเก็บหัวข้อเป็น**รายการกลาง** (`tbl_attribute`) แล้วค่าของแต่ละสินค้าชี้ไปที่หัวข้อด้วยรหัส
ตารางเปรียบเทียบต้องรู้ว่า "ความละเอียดกล้อง" ของสินค้า A กับ B คือแถวเดียวกัน — ถ้าหัวข้อเป็นข้อความอิสระ สะกดต่างกันนิดเดียว (`ความละเอียด` / `ความละเอียดกล้อง` / `Resolution`) ก็กลายเป็นคนละแถว

| | 1. ย้ายเข้าตารางของเรา แล้วให้เว็บจริงอ่านจากตารางของเรา (แนะนำ) | 2. ย้ายเข้าตารางของเรา แต่เก็บ `tbl_item_feature` ไว้ใช้ต่อด้วย | 3. แก้โค้ดของเราให้อ่าน/เขียน `tbl_item_feature` ตรงๆ |
|---|---|---|---|
| ทำอะไร | ย้ายครั้งเดียว → หน้าสินค้า/หลังบ้านของเว็บจริงเปลี่ยนไปอ่าน-เขียน `tbl_attribute_value` · `tbl_item_feature` เลิกใช้ (ไม่ลบ เก็บเป็นสำรอง) | ย้ายครั้งเดียว → ทั้งสองระบบใช้ตารางของตัวเอง | ไม่ใช้ `tbl_attribute*` เลย หัวข้อ = ข้อความใน `title` |
| ข้อดี | ข้อมูลมีที่เดียว · รวมหัวข้อซ้ำได้ · ใช้สเปคเฉพาะโมเดล + นำเข้า Excel ได้ครบ | เว็บจริงไม่ต้องแก้เลย | ไม่ต้องย้ายข้อมูล |
| ข้อเสีย | ต้องแก้ส่วนแสดงสเปคของเว็บจริง (แบบ B แก้ใน repo เขาอยู่แล้ว) | **ข้อมูลสองที่ แก้ที่หนึ่งอีกที่ไม่ตาม** — แอดมินต้องกรอกซ้ำ ไม่แนะนำระยะยาว | เสียสเปคเฉพาะโมเดล · หัวข้อสะกดต่างกันแยกแถวในตาราง · เปลี่ยนชื่อหัวข้อต้องแก้ทุกแถว · ต้องเขียน `search.js`/`products.js`/`admin.js`/`importPlan.js` ใหม่หลายจุด |

**ขั้นตอนย้าย (ข้อ 1 และ 2)** — เขียนเป็นสคริปต์ `database/merge/003_import_item_feature.sql` ได้ แต่ต้องดูข้อมูลจริงก่อน:
1. สร้าง `tbl_attribute` จาก `title` ที่ไม่ซ้ำ (ตัดช่องว่างหน้า-หลัง)
2. คัดลอก `desc` เป็น `tbl_attribute_value.value` (`model_code` ว่าง = ค่าร่วมทุกโมเดล) ข้ามสินค้าที่มีค่าหัวข้อนั้นอยู่แล้ว (รันซ้ำได้)
3. ใช้หน้า **คุณสมบัติ** ของหลังบ้านไล่รวมหัวข้อที่ความหมายเดียวกัน (เหมือนที่ทำกับสำเนา 25 ก.ย. — รวมได้ 9 คู่)

**ถ้าพบว่ามีข้อมูล ต้องขอจากทีมเว็บจริงก่อนเขียนสคริปต์:**
- จำนวนแถว และตัวอย่าง `title` / `desc` สัก 20–30 แถว — ดูว่าหัวข้อสะกดสม่ำเสมอแค่ไหน
- `desc` ยาวสุดเท่าไร และมี HTML / ขึ้นบรรทัดใหม่ / หลายค่าในช่องเดียวไหม — `tbl_attribute_value.value` ของเรายาวได้ 255 ตัวอักษร ถ้ายาวกว่าต้องขยายคอลัมน์ (ห้ามตัดทิ้ง)
- `tbl_item_type_feature` ใช้ทำอะไร (น่าจะเป็นชุดหัวข้อต่อหมวดหมู่) — ถ้าใช่ ใช้เป็นรายการหัวข้อตั้งต้นได้ดีกว่าดึงจาก `title`
- ส่วนไหนของเว็บจริงอ่าน/เขียน `tbl_item_feature` บ้าง (หน้าสินค้า, หลังบ้าน :3304, API :3302)

## 5. เรื่องที่ต้องตัดสินใจ / แก้ก่อนเปิดใช้กับ DB จริง

### 5.1 ✅ ระบบล็อกอินหลังบ้าน — ใช้ของเว็บจริง (ตัดสินใจ 1 ต.ค. 2026)

**ไม่ย้าย** `routes/auth.js`, `middleware/auth.js`, `utils/tokenBlacklist.js` และ `AdminLoginPage.vue` ของเราเข้า repo เขา · สิ่งที่ต้องทำตอนย้าย:
- `routes/admin.js` และ `routes/adminImport.js` เปลี่ยน `router.use(authMiddleware)` เป็น middleware ตรวจสิทธิ์แอดมินของ :3302
- หน้าหลังบ้านของเรา (คุณสมบัติ / โมเดล / นำเข้า Excel ฯลฯ) ย้ายเข้าไปอยู่ใต้หลังบ้าน :3304 ใช้ session/token ของเขา ไม่ต้องมีหน้าล็อกอินแยก — ตัด `stores/auth.ts` และ guard ใน router ของเราออก ใช้ guard ของเขาแทน
- ต้องถามทีม: middleware ตรวจสิทธิ์ของเขาชื่ออะไร / ใส่ข้อมูลผู้ใช้ไว้ที่ไหนใน `req` และหน้าหลังบ้านแนบ token ไปกับ API แบบไหน
- ⚠️ จาก bundle ของหน้าร้าน :3305 token ถูกเซ็นในฝั่ง client ด้วย secret ที่ฝังใน bundle (ตรวจ 28 ก.ย.) — ถ้าหลังบ้าน :3304 ใช้แบบเดียวกัน ใครก็ปลอม token แอดมินได้ ควรแจ้งทีมก่อนเอา endpoint เขียนข้อมูลของเราไปผูก

ข้อมูลเดิม (ตอนยังใช้ระบบของเรา): `routes/auth.js` ให้ **ทุกแถวใน `tbl_users` ที่ `flag = '1'`** ล็อกอินหลังบ้านได้
**ยืนยันแล้ว 29 ก.ย. 2026:** `tbl_users` ของเว็บจริงเก็บเฉพาะแอดมิน ทุกค่า `type` เป็นแอดมิน ไม่มีบัญชีลูกค้า → ไม่ต้องเพิ่มเงื่อนไข `type`
ถ้าวันหนึ่งเว็บจริงเพิ่มบัญชีลูกค้าลงตารางนี้ ต้องกลับมาเพิ่มเงื่อนไขใน `findFirst` ของ `/login`

### 5.2 ที่อยู่รูปภาพ

| | ค่าใน `tbl_item.itm_image_master` | เสิร์ฟที่ |
|---|---|---|
| สำเนานี้ | `/uploads/products/2026-09/xxx.jpg` | backend ของเรา `/uploads/...` |
| เว็บจริง | `2024-12/xxx.jpg` (ไม่มี `/` นำหน้า) | `:3302/api/image/<ค่านั้น>` |

ต่อ DB จริงแล้วรูปของสินค้าเดิมจะแตก จนกว่าจะแก้ **จุดเดียว** ในแต่ละฝั่ง:
- เว็บ: `resolveImageUrl()` ใน `frontend/src/services/api.ts` — ค่าที่ไม่ขึ้นต้นด้วย `/` หรือ `http` ให้ต่อหน้าด้วย `/api/image/` ของเว็บจริง
- แอป: `ApiConfig.imageUrl()` ใน `mobile/lib/config/api_config.dart` — กติกาเดียวกัน

รูปที่แอดมินอัปโหลดผ่านระบบนี้จะถูกเก็บใน `database/uploads/` → ต้องตัดสินใจว่าจะเก็บต่อที่นี่ หรือย้ายไปที่เดียวกับเว็บจริง

### 5.3 path ของ API

path ของเรา (`/api/products`, `/api/search`, `/api/categories`, `/api/banners`, `/api/shops`, `/api/footer`, `/api/logs`, `/api/compare`, `/api/auth`, `/api/admin/*`)
**ไม่ชนกับ** path ที่หน้าร้านจริงเรียก (`/api/product/…`, `/api/searchProduct/…`, `/api/banner`, `/api/shop/…`, `/api/footer-list`, …)
แต่อาจชนกับ path ฝั่งหลังบ้านของเว็บจริง (`/api/auth`, `/api/admin`) ซึ่งเราไม่เห็นโค้ด
ถ้ารันบนโดเมนเดียวกัน แนะนำให้ reverse proxy แยกด้วย prefix เช่น `/compare-api/` → backend ของเรา แล้วแก้ `baseURL` ใน `frontend/src/services/api.ts` และ `ApiConfig.baseUrl` ของแอปให้ตรง

### 5.4 ค่าที่ต้องตั้งตอนรันจริง

`backend/.env`: `DATABASE_URL`, `JWT_SECRET` (สุ่มใหม่ — ขาดแล้ว backend ไม่ยอมเปิด), `NODE_ENV=production`, `TRUST_PROXY=1` (อยู่หลัง nginx — ไม่ตั้งแล้ว rate limit นับทุกคนเป็น IP เดียว)
รายละเอียดใน [deployment.md](./deployment.md)
